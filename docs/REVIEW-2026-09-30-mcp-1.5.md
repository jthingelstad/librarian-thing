# Review 2026-09-30: the Librarian MCP at 1.5.0

A second pass over the connector the day after 1.5.0 shipped, at Jamie's
request ("can we do more evaluation of the new mcp interface and see if
anything further can be improved?"). Reviewed at `1.5.0+tools`, librarian-thing
`main` at 66e8c92c. **Applied the same day as 1.5.1: items 1 to 12. See
the Outcome below; the rest of this document is the review as written.**

**Method.** Dumped the exact `tools/list` and `initialize` from the built
registry and ran the census on them. Ran 36 local probes against `dist/` with
the live S3 corpora (read-only), including five spellings of one URL, two
short domains, and three list_content topics checked against a full-text
count of the weekly corpus (`corpus.json`, generated 2026-09-30 01:24 UTC).
Read the matcher and filter code behind every surprising number. The call log
was not re-read.

This review does not revisit the 09-29 review or the approved plan. Anything
already scheduled for Phase 4 (annotations, outputSchema, grouping the skim,
argument aliases, window idioms) appears only as a pointer.

  it fell only 30.5K to 28.5K. The terms were never the bulk. Per-year

  - Three domains a year.
  - `limit` now sets how many years come back, newest first, with a

## The short answer

Search itself is good. `search_archive` with `voice: jamie` returns Jamie's
own RSS commentary from WT336, WT173, WT253, WT227 and WT298. `compare_eras`
contrasts 2017-19 ("I've always been a big user of RSS") with 2024-26 ("MCP
totally reminds me of RSS") well. `find_links` normalises URLs: five spellings
of one link (no trailing slash, `http`, `?utm_source`, `www.`) all find WT74.

The problems are in the **counting and filtering** tools, which is where
Jamie's archive most needs to be exact. Four verified defects make
`archive_lens`, `list_content` and `find_links` return wrong sets. The worst
one makes "when did Jamie write about RSS" answer 349 issues, of which 89
mention RSS, and name WT351 as the latest mention. WT351 never says RSS.
All four are MCP-only fixes in `archive-lens.mts` and `archive-tools.mts`, so
the Fri 10-02 freeze permits them.

## Part 1: verified defects

### D1. Topic-label false matches in archive_lens and list_content

Every Weekly Thing chunk carries its issue's `topics`. These are up to six of
the nine coarse labels that `detect_topics` assigns by keyword
(`librarian-core/librarian_core/corpus.py:41`, `:290`). One occurrence of
"web", "blog", "feed" or "podcast" earns "Open web and RSS", so 8,856 of the
8,930 chunks carry it.

- `archive_lens` puts `topics` in the matched text (`shared/archive-lens.mts:148`
  `lensHaystack`, and `:170` `lensMatchReasons`).
- `list_content` does the same (`shared/archive-tools.mts:1394`
  `sourceMatchesTopic`, `:1426`).
- The internal `list_issues` does too (`:1630`).

As a result, any query word that appears in a label matches the label.

| Query | Issues whose text says it | Issues the lens matches |
|---|---:|---:|
| RSS | 89 | 350 |
| agents | 45 | 214 |
| travel | 44 | 133 |
| web3 | 42 | 137 |
| culture | 137 | 278 |
| personal sites | 2 | 24 |

- Live, `archive_lens {topic: "RSS"}` reports 349 Weekly Thing sources and
  9,205 evidence matches.
- `latest` is `wt-351`, whose only match reason is `topics: 'RSS'`.
- `first` and `latest` are meant to come only from strict matches (the comment
  above `archive-lens.mts:497`). That guard doesn't help here, because
  `strict` is also computed over the label haystack (`:465`, `:265`).
- `list_content {topic: "RSS", source_kind: "weekly_thing"}` returns
  `total_count: 349`.
- `voice: jamie` can't narrow the lens either. Every issue already matched by
  label, so its per-year counts are identical to the unfiltered lens.

**Fix.** Take `topics` out of the text haystack. Keep one path: a query that
names a whole label ("Open web and RSS") still matches that label, so a lens
over a `list_topics` cluster keeps working. Add a regression test pinning
"RSS" against a chunk whose only RSS is its label.

### D2. list_content reads only an issue's first 12 chunks

`sourceMatchesTopic` reads `chunks.slice(0, 12)` (`archive-tools.mts:1402`),
but 344 of 353 issues have more than 12 chunks (the largest has 49). A mention
past the twelfth chunk is invisible, so the tool undercounts every term that
does not also hit a label.

| Query | Issues that mention it | list_content total_count |
|---|---:|---:|
| Mastodon | 12 | 7 |
| Datasette | 10 | 4 |

D1 and D2 pull the counts in opposite directions, so a total can look
plausible and still be wrong.

**Fix.** Scan every chunk, as the lens already does. list_content runs in
21-31 ms today, so there is room.

### D3. Domain filters are substring matches

`find_links` (`archive-tools.mts:766`) and `list_content` (`:1475`) test
`normalizedDomain(value).includes(domain)`.

- `find_links {domain: "x.com"}` returns 154 links and none of them are x.com:
  netflix.com (12), vox.com (10), sanebox.com, dropbox.com, spacex.com,
  fox.com and more.
- `{domain: "om.co"}` returns 149 links, 33 of them om.co, alongside
  fandom.com, intercom.com and usefathom.com.

**Fix.** Match when the domain equals the query or is a subdomain of it
(`d === q || d.endsWith('.' + q)`), after the existing `www.` strip.
`domain: "netflix.com"` still finds media.netflix.com.

### D4. find_links truncates silently, oldest first

find_links pushes the first `limit` links in corpus order and stops
(`archive-tools.mts:776`). For example, `{domain: "simonwillison.net"}` has
`total_count: 69`, and the 20 returned run 2017-10 to 2023-10. The most
recent 49 links, all of 2024-26, are unreachable except by guessing a
`year_range`. There is no `sort`, no offset, and no note that anything was
left out.

This is the lookup the link wand's "linked before" needs (WB item 14).

**Fix now.** Add `results_omitted` and a note ("69 matched; 20 shown, oldest
first; pass year_range or a narrower filter").

**Needs a nod.** Default to newest first, which is what every other list tool
does, and add an optional `sort: newest | oldest`.

### D5. get_source sends the whole issue twice

With no `section` filter, get_source returns the issue body as `body` and
every section's text again in `section_texts` (`archive-tools.mts:659-663`,
`:714-715`). For `wt-351` that is 13,880 and 13,772 characters of the same
text in a 42,651-character result.

**Fix.** When there is no filter, keep `body` as the one full text and give
`section_texts` headings and lengths only; the full section text still comes
back when a filter asks for it. Expected size is about 29K.

The field stays, but its entries lose `text` in one case, so this needs a nod.

### D6. on_this_day truncates when windowed

`on_this_day {window_days: 3}` returns 21 years × up to 5 items (95 items)
and hits the result cap at 47,369 characters (TRUNC). The unwindowed call is
14K.

**Fix.** When `window_days > 0` and `limit_per_year` is absent, default it to
2 (an explicit value is still honoured). Drop the six `photo.alt: null`
fields. Don't send `title` when it equals `label`.

### D7. Tool descriptions give Jamie a pronoun

Four descriptions in `prompts/tool-specs.json` use a pronoun for Jamie:

- quote_search, `:430`
- compare_eras, `:624`: "keeps only his own words"
- claim_check's `voice`, `:832`: "what Jamie himself wrote, never what he quoted"
- currently_history, `:914`: "what games has he played"

The blog abstracts adopted a no-pronoun rule on 09-29; these should follow it
("Jamie's own words", "what Jamie quoted").

## Part 2: size and noise (no defect, worth trimming)

Measured rendered sizes:

| Call | Chars | What dominates |
|---|---:|---|
| get_source wt-351 | 42,651 | D5 duplication |
| source_neighborhood wt-351 | 39,070 | outgoing_links 20K, related_sources 11K |
| corpus_stats | 30,528 | `yearly_signals` 21K of it |
| archive_lens RSS | 22,768 | `sources_by_id` 15K (19 of 410 sources) |
| search_archive | 15-16K | text plus a 450-char skim per hit |
| find_links domain | 14,140 | 20 links at 680 chars each |
| on_this_day | 14,118 | fine unwindowed; see D6 |
| list_topics | 12,599 | fine |
| compare_eras | 12,090 | fine |

- **source_neighborhood.**
  - `cross_source_links` repeats entries verbatim from `outgoing_links`
    (5 of 5 for wt-351, 2 of 3 for a blog post). Send them as ids, or flag
    `cross_source: true` on the outgoing entry.
  - Each `related_sources` entry carries a full `domains` list (up to 700
    chars), `audio_url`, and both `description` and `abstract`. Cap domains
    at 5, as `oldest`/`newest` in corpus_stats already do.
- **corpus_stats.** `yearly_signals` has noise terms: "micropost" (304, blog
  2026), "wt350", "day", "great", "time", "first". Add them to the stoplist
  and cut each year to its top 5 terms. That should roughly halve the call.
- **The coarse labels ride every hit.** search, compare_eras, quote_search,
  get_source and lens records all carry `topics`: up to six of the nine
  labels, about 120 chars, true of nearly every issue. They tell an agent
  nothing and invite D1-style reasoning. Proposal: drop them from hits in 2.0
  (Phase 4). `list_topics` clusters stay as they are.
- **A Weekly Thing skim's `abstract` is the issue's greeting.** For WT336 it
  reads "Good morning! ☕️ I hope your weekend is getting off to a great
  start… cold start to our winter"; for WT351, "Hello there! First a quick
  welcome…". It is `summarize_text(body)` (`corpus.py:931`), the opening
  paragraph, not an abstract. The issue `description` ("Crucial exits consumer
  RAM, AI transforming work at Anthropic, Perl's cultural decline…") is the
  useful line.
  - **Now (MCP-only):** send only `description` in a weekly skim.
  - **Product call P3:** generate real issue abstracts.
- **quote_search** hits carry the issue's full `domains` list and `audio_url`;
  neither helps verify a quote.

## Part 3: surface consistency

Already scheduled for Phase 4, listed so nothing is lost:

- no `annotations`, no `outputSchema`
- `additionalProperties` absent; the server refuses unknown arguments at
  runtime (`find_links {sort}` answers `unknown argument "sort"`)
- claim_check's four undescribed aliases
- `year` / `year_start`/`year_end` / `year_range` drift (media_search,
  currently_history, top_references)
- the per-hit skim

New, and cheap to do in 1.5.x:

- **initialize instructions** (659 chars, `shared/mcp.mts:416`) never mention:
  - `on_this_day`, `list_topics` or `compare_eras`
  - `voice: jamie`
  - the id forms an agent can pass back (`wt-351`, `blog-<id>`, `ep-<n>`)

  Two sentences cover all of it.
- **36 arguments** have neither a description nor an enum; the
  `match_mode`, `case_sensitive`, `year_range` and `voice` descriptions are
  repeated 4-8 times. Descriptions for the 36 are additive; deduplication
  waits for 2.0.
- **archive_lens** returns `results` and `timeline` as the same list when
  `operation: timeline` (459 chars; small, but it reads as two answers).
  Phase 4.
- The archive_lens description is 1,505 chars, and both lens tools repeat
  the same "Response shape" paragraph. Phase 4.

Checked and working as designed: `reading_path` entries marked
`resolved: false` (`wt-35` in the voice=jamie lens) are sources dropped by the
size cap, not bad ids. Another Thing really has one episode, so the podcast
stats are right.

## Part 4: product calls

- **P1. find_links order.** Newest first by default, plus `sort`? The
  trade-off: agents that assumed chronological order (none known) would see a
  different first page. Recommend yes; "linked before" needs the recent end.
- **P2. The nine coarse labels.** They are keyword counts rather than
  curation, and nearly every issue carries "Open web and RSS". Options:
  1. keep them as `list_topics` clusters only, out of hit shapes (the
     Part 2 proposal)
  2. rebuild them from the graph's topics
  3. retire them

  This is a corpus change, so it lands after WT352 if at all.

  `list_topics` also surfaces graph topics that are not topics: "After",
  "Blog", and domains ("macstories.net", "github.com") alongside "MacStories".
  That is graph quality, and the graph also feeds weekly.thingelstad.com topic
  pages.
- **P3. Real Weekly Thing abstracts.** 352 issues through the same Sonnet
  batch pipeline as the blog abstracts, at a fraction of the blog run's cost.
  Corpus change, after WT352.
